## Interaction contract

Provider setup and application selection belong in focused controls around a stable task composer. Missing prerequisites explain their repair. A running task shows its goal and current subgoal. Required approval is the primary next action; routine activity remains secondary. Errors retain useful context and require fresh observation rather than replaying an old effect.

Guided tasks require human confirmation at finish and remain labeled user-confirmed. Native value readback, an executor's explicit checks, and independently verified persistence are different evidence. See the [technical specification](../technical-spec.md), [reviewed fill contract](../verified-fills.md), and [agent bridge](../agent-bridge.md) for the corresponding execution paths.

Below the width where both panes remain usable, Task/App view controls should retain content and scroll position. Stop and execution status must remain available. Modal dialogs trap and restore keyboard focus; status updates must not move focus. Long lists, proposed values, and activity scroll within their own surfaces.

Dictation is optional editable task input. It cannot submit a task or grant approval. Recognition availability, on-device support, and permissions are capability gates, with no cloud fallback. Late cancelled results must not replace a newer draft.

Layout patterns do not change authority. The original read-only developer server prepares values but cannot execute them. The executable MCP bridge uses explicit launcher scope and host-owned task authorization, while Electron keeps its own guided-action and reviewed-fill interfaces. UI changes must preserve those distinctions.
